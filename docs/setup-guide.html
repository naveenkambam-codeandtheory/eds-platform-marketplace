How the model works

Read this first — the procedures assume it

Several brands share one codebase. Something needs to look or behave differently. The instinct is to copy the block and change it. Do that twenty-five times across three brands and you maintain seventy-five implementations, where every accessibility fix is applied three times and the third one is forgotten.

So the platform is built around one question, asked before any code is written: can this difference be expressed as data instead? Different content, different token values, a variant class, or a capability flag. Only when all four genuinely fail is a second copy of the code written, and then it is written down and reviewed like the liability it is.

L4 · BRAND
Changes per brand Tokens, content, icons, fonts, one registry entry. No JavaScript. The only layer a new brand touches.
L3 · BLOCKS
Shared experience Brand-agnostic by default, configuration-aware. Reads the brand through the platform, never by inspecting the URL.
L2 · PLATFORM
Bootstrap scripts.js, brand.js, shared utilities. Knows about brands so blocks do not have to.
L1 · CORE
Never modified aem.js and the EDS pipeline. Upstream code — extend in scripts/lib/.

Dependencies point downward only. Blocks reach the brand layer through CSS custom properties and a configuration object. A block that imports a brand file, or tests a brand name inline, has broken the model.

The number that matters

The fork ratio is the share of blocks existing in more than one brand-specific copy. Target under 15%; over 20% triggers an architecture review rather than an approval. CI reports it on every pull request. It is the single metric that predicts whether the next brand takes a week or a quarter, and it only ever moves in the wrong direction quietly.

Part 1 · Create the project

Steps 1–6 · from empty to a site rendering locally

  1. Create the repository from the boilerplate

    Start from Adobe's boilerplate rather than an empty repository. It ships the block collection, lint configuration, the loading-phase scaffolding, and an AGENTS.md you will extend in step 13.

    Open github.com/adobe/aem-boilerplate and choose Use this template. If your content will live in Document Authoring, use the DA-compatible variant, aemsites/da-block-collection.

    git clone https://github.com/YOUR-ORG/YOUR-PROJECT.git
cd YOUR-PROJECT
npm install
    CHECK

    blocks/, scripts/aem.js, styles/styles.css and head.html all exist.

  2. Install AEM Code Sync

    This GitHub App watches the repository and publishes each commit. Without it nothing you push reaches a preview URL.

    Install github.com/apps/aem-code-sync and grant it access to the new repository.

    CHECK

    The App appears under the repository's Settings → GitHub Apps, and a commit to main shows a check run.

  3. Connect the content source

    Content lives outside the repository, and the binding between the two is held in the Configuration Service. On current projects there is no fstab.yaml: configuration is site-level rather than repository-level, and it is managed through a user interface or an API.

    The AEM Code Sync bot creates an initial configuration when you install it. To set or change the content source, use the site admin tool at tools.aem.live, which is the right option for almost everything. The service is API-first, so the same thing can be scripted:

    Configuration Service — set the content source 
    curl -X POST https://admin.hlx.page/config/YOUR-ORG/sites/YOUR-SITE.json \
  -H 'content-type: application/json' \
  -H 'x-auth-token: <your-auth-token>' \
  --data '{
    "version": 1,
    "code":    { "owner": "YOUR-ORG", "repo": "YOUR-PROJECT" },
    "content": { "source": { "url": "<content-source-url>" } }
  }'

    Your Adobe user has to be mapped as an admin on the GitHub organisation before the service will accept changes. Sort that out first — it is the step that most often blocks a morning.

    Two ways to lay out several brands — decide now

    One site, path prefixes. /alpha/, /beta/ under a single site. Brand stays visible in preview URLs, local development, analytics, and the sidekick, with no per-environment DNS work, and production hostnames map onto the prefixes at the CDN. Simplest operationally, and what the rest of this manual assumes.

    Repoless: one code repository, one site per brand. Because configuration is no longer tied to the repository, the same code can drive several sites, each with its own content source, hostname, and configuration. Cleaner separation and independent publishing per brand, at the cost of managing N site configurations instead of one.

    Both work with everything in this framework; only brand resolution differs. With path prefixes, the path match does the work. With repoless, set pathPrefix to "/" for each brand and let the theme metadata and the hostname entries resolve it — which is why the resolution order in step 10 covers all three.

    Choose before any content exists. Changing later means redirecting every URL.

    Inheriting an older project

    Sites created before the Configuration Service still carry fstab.yaml and .helix/config.xlsx. Those remain supported but are not receiving further investment, and fstab.yaml permits only one mountpoint — a hard limit for multi-brand work. Migrate to the Configuration Service and delete the legacy files rather than running both. Query index configuration moves the same way, out of helix-query.yaml and into the service.

    CHECK

    A test document in the content source previews at its .aem.page URL, and the site configuration at tools.aem.live shows the content source you expect.

    aem up          # serves on http://localhost:3000 against your content source
    CHECK

    The page renders at localhost:3000 and edits to files under blocks/ appear on reload.

    The boilerplate ships ESLint (Airbnb base) and Stylelint. Get to zero warnings now, while the repository is empty, so the first real change is not competing with pre-existing noise.

    CHECK

  1. Describe the project's shape

    platform.json tells every script in this framework what actually varies for this project. The scripts default to the standard boilerplate layout — blocks/, styles/brands/, brands.json, icons/, fonts/, and the rest — without needing it spelled out here, so this file captures only the two things that are genuinely policy: conventions and budgets.

    platform.json 
    {
  "platform": "aem-eds",
  "conventions": {
    "forkPrefix":       "{brandKey}-",
    "brandAttribute":   "data-brand",
    "allowedLiteralColors": ["#fff", "#000"]
  },
  "budgets": { "forkRatioTarget": 15, "forkRatioMax": 20, "brandTokenFileKb": 8 }
}
    Why this file?

    What it is: a small config file that this framework's own scripts (validate-tokens.mjs, validate-skills.mjs, onboard-brand.mjs) read instead of hardcoding this project's naming rules and budgets.

    Why you need it: without it, every script would carry its own assumptions about what a forked block is named, what attribute brand styling hangs off, which literal colours are allowed, and what the fork-ratio and token-file-size limits are. One file means one place to change any of that — and the same scripts run unchanged on the next multi-brand project.

    Fields:

    • platform — a fixed identifier ("aem-eds") scripts can branch on if this framework is ever ported to another platform.
    • conventions.forkPrefix — the directory-naming pattern ({brandKey}-) that marks a block as an L4 fork, so tooling can tell a fork from a shared block by name alone.
    • conventions.brandAttribute — the DOM attribute (data-brand) that carries the resolved brand key; CSS and scripts key off it instead of a hardcoded selector.
    • conventions.allowedLiteralColors — the short allow-list of literal colour values (#fff, #000) exempt from the no-hardcoded-colours lint rule, because true black/white are structural, not brand.
    • budgets.forkRatioTarget — the fork ratio (%) CI treats as healthy.
    • budgets.forkRatioMax — the fork ratio (%) that fails CI outright.
    • budgets.brandTokenFileKb — the maximum size, in KB, of a single brand's token file before the validator flags it as carrying more than tokens.
    Why there is no paths block

    A companion critique of this framework flags a paths block here as speculative generality: every boilerplate-derived EDS repository has this exact layout, so the scripts already default correctly without it — verified, not assumed. conventions and budgets stay, because those are policy and do get argued about.

    Add a paths block later, scoped to only the entries that actually differ, the day a project's layout genuinely diverges from the boilerplate default. Until then it is nine lines that will be copy-pasted identically forever.

    CHECK

    node -e "JSON.parse(require('fs').readFileSync('platform.json'))" exits without error.

Part 1 · Wire the brand layer

Steps 7–12 · the machinery that makes brands data

  1. Create the brand registry

    brands.json is the only place a brand is declared. Everything else reads from it. Start with one brand; the onboarding command adds the rest.

    brands.json 
    {
  "default": "alpha",
  "brands": {
    "alpha": {
      "key":        "alpha",
      "name":       "Alpha",
      "pathPrefix": "/alpha",
      "hosts":      ["alpha.example.com"],
      "locales":    ["en-us"],
      "indexPath":  "/alpha/query-index.json",
      "features":   { "commerce": false, "storeLocator": true },
      "endpoints":  { "catalog": "/api/alpha/catalog" }
    }
  }
}
    Why this file?

    What it is: the single registry where every brand this codebase serves is declared — key, path prefix, hostnames, locales, capability flags, API endpoints.

    Why you need it: brand.js imports it directly (no network fetch) to resolve which brand a page belongs to before first paint, and it's what turns onboarding a new brand into "add one object here" instead of hunting down every place a brand name is hardcoded across scripts and blocks.

    Fields (per brand):

    • key — the lowercase, hyphen-free identifier used everywhere: file names, the data-brand attribute, directory names, content metadata.
    • name — the human-readable brand name, for display and tooling output only.
    • pathPrefix — the URL prefix this brand's content lives under ("/alpha"), or "/" on a repoless, one-site-per-brand setup.
    • hosts — production hostnames matched when path resolution doesn't apply — the main signal on a repoless setup.
    • locales — the brand's locale(s); the first entry sets <html lang>.
    • indexPath — where this brand's generated query-index.json lives, so listing/search blocks never read another brand's content.
    • features — capability flags (commerce, storeLocator) blocks branch on instead of a brand name.
    • endpoints — this brand's API base paths, so a block calls a name from the registry instead of a hardcoded URL.

    Brand keys are lowercase alphanumeric, no hyphens, and are used verbatim everywhere: file names, the data-brand attribute, directory names, and content metadata. An inconsistent key is the most common cause of a token file that silently never loads.

    On a repoless setup where each brand is its own site, set pathPrefix to "/" and make sure hosts is populated — resolution then falls to the theme metadata and the hostname rather than the path.

    Features are capabilities, never brand names. commerce and storeLocator are correct; isAlpha is not. This is what lets a future brand opt in through this file alone.

  2. Define the token contract

    The contract is the fixed set of semantic token names every brand must define. CI fails when one is missing, which prevents the worst failure mode in multi-brand theming: a new brand silently inheriting another brand's colours because a variable fell through.

    styles/tokens/contract.json 
    {
  "version": 1,
  "tokens": {
    "colour": ["--color-accent","--color-accent-hover","--color-accent-contrast",
               "--color-text","--color-text-muted","--color-text-inverse",
               "--color-surface","--color-surface-raised","--color-surface-inverse",
               "--color-border","--color-focus","--color-danger","--color-success"],
    "type":   ["--font-heading","--font-body","--font-mono",
               "--font-size-xs","--font-size-s","--font-size-m","--font-size-l",
               "--font-size-xl","--font-size-2xl","--font-size-3xl",
               "--line-height-tight","--line-height-base","--line-height-loose"],
    "space":  ["--space-1","--space-2","--space-3","--space-4","--space-6",
               "--space-8","--space-12","--space-16","--space-section","--space-gutter"],
    "shape":  ["--radius-none","--radius-s","--radius-m","--radius-l","--radius-full",
               "--shadow-s","--shadow-m","--shadow-l"],
    "layout": ["--layout-max-width","--layout-content-width"],
    "motion": ["--duration-fast","--duration-base","--duration-slow","--easing-standard"],
    "brand":  ["--brand-logo","--brand-logo-inverse","--brand-favicon"]
  }
}
    Why this file?

    What it is: the fixed list of semantic token names — colour, type, space, shape, layout, motion, brand — that every brand's CSS file must define a real value for.

    Why you need it: without a contract, a brand file missing a token silently inherits whichever other brand's stylesheet happened to load first — a wrong colour that surfaces on one page, weeks later, in production. CI treats a missing or stubbed token as a build failure specifically to catch this before it ships, instead of trusting every brand file to be complete by inspection.

    Fields:

    • version — bump when the contract's shape changes, so tooling can detect a stale copy.
    • tokens.colour — every colour role a brand must supply: accent, text, surface, border, focus, danger/success states.
    • tokens.type — typefaces, the mono stack, and the full type scale (sizes and line-heights).
    • tokens.space — the spacing scale, plus section and gutter spacing.
    • tokens.shape — corner radii and elevation (shadow) steps.
    • tokens.layout — max content width and content width.
    • tokens.motion — animation durations and easing.
    • tokens.brand — brand-identity assets: logo, inverse logo, favicon.

    Adjust the names to your design system, but keep them role-based rather than brand-prefixed. In a multi-brand system every token is brand-scoped by definition, so --brand-primary says nothing that --color-accent does not — and a name describing what a token does survives a rebrand, while a name describing what it is does not.

    Adding a token later is a breaking change

    Every brand must supply a value. Adding one ships in a single commit that also fills it for every existing brand. Renaming is worse than adding: add the new name, migrate usages, remove the old one in a later release, so no brand breaks mid-flight.

    One name, two real roles — split it, don't force it

    A baseline contract is a starting guess. Real brand data sometimes shows that one assumed token is actually two distinct roles wearing the same name — a brand using a muted colour for plain text links and a completely different, bolder colour for CTA buttons and heading emphasis is not "one accent colour," it's --color-accent and a separate --color-link. The same thing happens with type: a brand whose body text is one flat size at every viewport, but whose headings resize independently at each of six levels, can't share a single --font-size-m between "the size of this paragraph" and "the size of this heading" — the two need their own names (e.g. --font-size-m for flat body/UI copy, --font-size-heading-m for the responsive heading scale).

    The tell is a token whose real value depends on which caller is asking. When that happens, verify against the actual design (production computed styles beat a guess every time) before deciding the split — and add the second name to every existing brand's file in the same commit, same as any other contract addition.

  3. Write the first brand token file

    Custom property definitions only. No element or class selectors, no layout rules, no component styling. A brand file containing .cards { … } is a fork wearing a token file's clothes, and the validator rejects it.

    styles/brands/alpha.css 
    :root[data-brand='alpha'] {
  /* private primitives — brand-internal, not part of the contract */
  --alpha-blue-600: #0B5FFF;
  --alpha-blue-700: #0847C4;

  /* the contract */
  --color-accent:          var(--alpha-blue-600);
  --color-accent-hover:    var(--alpha-blue-700);
  --color-accent-contrast: #fff;
  --font-heading: 'Alpha Display', system-ui, sans-serif;
  --font-body:    'Alpha Text', system-ui, sans-serif;
  --radius-m: 4px;
  --layout-max-width: 1280px;
  --brand-logo: url('/icons/alpha/logo.svg');
  /* …every remaining contract token… */

  /* optional component-level overrides */
  --header-height: 72px;
}

@font-face {
  font-family: 'Alpha Display';
  src: url('/fonts/alpha/display.woff2') format('woff2');
  font-display: swap;
  size-adjust: 100%;      /* match fallback metrics so swapping does not shift layout */
}
    Why this file?

    What it is: one brand's actual token values — custom property declarations only, no selector beyond :root[data-brand='<key>'] and @font-face.

    Why you need it: this is where a brand's colours, type, spacing, and logo actually live, and it's the mechanism the whole framework is built around — most differences between brands should be solvable here, or with a component-token override, instead of by forking a block's code.

    What's inside:

    • private primitives — brand-internal raw values (e.g. --alpha-blue-600) that exist only to be referenced below; nothing outside this file should use them directly.
    • the contract — every token name contract.json requires, given this brand's real value.
    • component-level overrides (optional) — a token scoped to one component (--header-height), for the rare case a semantic token alone doesn't cover a brand difference.
    • @font-face — this brand's web fonts, with font-display: swap and a matched size-adjust to avoid layout shift on swap.
    Component-level tokens cover style choices too, not just values

    The obvious component-level override is a size (--header-height above). Less obvious, but just as real: a brand's structural style choices — headings uppercase or not, bold or not; buttons square or pill-shaped — belong here as tokens too, not as hardcoded rules in the shared CSS that reads them. A shared file writing text-transform: uppercase directly has baked one brand's identity into every brand's headings; writing text-transform: var(--heading-transform) and letting each brand's file supply uppercase or none keeps the shared file actually brand-agnostic. These aren't required contract entries — they default per brand, the same as any other component-level token:

    /* in styles/brands/alpha.css */
--heading-weight:    700;
--heading-transform: uppercase;
--button-radius:     var(--radius-none);   /* square CTAs, not the shared pill default */
--button-transform:  uppercase;

    Then styles.css reads font-weight: var(--heading-weight) and border-radius: var(--button-radius) — never the literal — so a second brand can choose lowercase, normal-weight, pill-shaped buttons without a single edit to shared code.

    CHECK

    The file is under 8 KB and contains no selector other than :root[data-brand='alpha'] and @font-face.

  4. Add brand resolution

    This runs before first paint, so it must be synchronous, allocation-light, and incapable of throwing. Precedence is metadata → path → host → default.

    Metadata comes first deliberately: it lets content teams stand up a brand section with no deploy, and it costs zero extra requests because it ships inside the served HTML. Path and host are the safety net.

    scripts/brand.js 
    import { getMetadata } from './aem.js';

// The registry is imported, not fetched. A fetch here costs a round trip before
// the brand stylesheet can even be requested, and a second before first paint -
// roughly 300 ms of LCP on a mid-tier mobile connection, on every page, for
// every brand. Generate this file from brands.json at commit time, or keep the
// two in sync with a CI check.
import REGISTRY from './brands.js';

let resolved;

const matchByPath = (p) => Object.values(REGISTRY.brands)
  .find((b) => b.pathPrefix !== '/' && (p === b.pathPrefix || p.startsWith(`${b.pathPrefix}/`)));

const matchByHost = (h) => Object.values(REGISTRY.brands)
  .find((b) => (b.hosts || []).includes(h));

export function getBrand() {
  if (resolved) return resolved;
  resolved = REGISTRY.brands[getMetadata('theme')]
    ?? matchByPath(window.location.pathname)
    ?? matchByHost(window.location.hostname)
    ?? REGISTRY.brands[REGISTRY.default];
  return resolved;
}

export const getBrandConfig = () => getBrand();
export const hasFeature = (f) => Boolean(getBrand().features?.[f]);
    Why this file?

    What it is: the module that resolves which brand the current page belongs to, in order: page metadata, then path prefix, then hostname, then a default.

    Why you need it: this runs before first paint, so it has to be synchronous and incapable of throwing — it can't be scattered logic re-derived in every block. It's the one place brand resolution lives; blocks call getBrand()/hasFeature() instead of each reimplementing "which brand am I" themselves.

    What each export does:

    • REGISTRY — the brand registry, imported as a module (not fetched) so resolution costs zero network round trips.
    • getBrand() — resolves and caches the current brand: metadata → path → host → default, in that order.
    • getBrandConfig() — an alias for getBrand(), for call sites that read better naming the config than the brand.
    • hasFeature(f) — the capability check every block should branch on instead of a brand name.
    Ship every brand's tokens in styles.css

    The obvious design gives each brand its own stylesheet and loads it once the brand is known. That serialises two requests before first paint, which is the opposite of what this platform is for.

    Token files are almost entirely custom property declarations, so they compress hard — four brands is on the order of 2–3 KB over the wire. Concatenating all of them into styles.css under [data-brand] selectors costs a few unused kilobytes and saves a full round trip on every page. Below roughly ten brands that trade is clearly worth it. Above it, or where brands differ by more than tokens, switch to per-brand loading and accept the request.

    On a repoless setup, this isn't optional — it's the only option. head.html is one file shared by every brand's site. A static <link> naming one brand's stylesheet would ship to every other brand's site too, which defeats the point. Per-brand loading, driven by getBrand() inside loadEager (step 11), is what keeps each site fetching only its own brand's CSS — concatenation has no equivalent here, because there's no single shared stylesheet request to concatenate into that every brand's site loads exactly once.

    Keep the source files separate either way — styles/brands/<key>.css is what the validator checks and what a brand team owns. Concatenation is a build-time or commit-time concern, not an authoring one.

  5. Hook resolution into the eager phase

    The boilerplate keeps body hidden until appear is added. Awaiting the brand token file there gives zero-flicker branding with no inline script in head.html — which matters, because head.html is shared by every brand and every byte in it is paid for on every page of every brand.

    scripts/scripts.js — inside loadEager 
    import { getBrand } from './brand.js';

async function loadEager(doc) {
  document.documentElement.lang = 'en';

  // Synchronous: no fetch, no awaited stylesheet. Tokens for every brand are
  // already in styles.css, which head.html loads. Setting the attribute is all
  // that is needed to select them.
  const brand = getBrand();
  document.documentElement.dataset.brand = brand.key;
  document.documentElement.lang = brand.locales[0];

  decorateTemplateAndTheme();
  const main = doc.querySelector('main');
  if (main) {
    decorateMain(main);
    document.body.classList.add('appear');
    await waitForFirstImage(main);
  }
}
    Why this file?

    What it is: not a new file — three lines added to the existing loadEager function, setting data-brand on <html> and the page's language before appear is added.

    • document.documentElement.dataset.brand = brand.key — sets data-brand, the attribute every brand-scoped CSS selector keys off.

    Load a page under the brand's prefix. In DevTools, <html> carries data-brand="alpha", the brand stylesheet is in the network waterfall before first paint, and there is no flash of unstyled text.

    Repoless: load the brand's CSS at runtime instead

    The version above assumes concatenation (step 10's note above explains why that's the default). On a repoless setup it can't apply — there's no way to write one head.html that loads a different stylesheet per site — so loadEager fetches the brand's file itself, kicked off immediately and awaited only once, right before content is revealed:

    scripts/scripts.js — repoless variant

document.documentElement.dataset.brand = brand.key;
document.documentElement.lang = brand.locales[0];

  .catch(() => console.error(`Could not load brand styles for "${brand.key}"`));

decorateTemplateAndTheme();
const main = doc.querySelector('main');
if (main) {
  decorateMain(main);
  await brandCSS;
  document.body.classList.add('appear');
  await waitForFirstImage(main);
}

    Started before decorateMain so it overlaps with DOM work instead of adding to it; awaited right before appear so there's no flash of the wrong brand's (or no brand's) styling; caught so a failed request doesn't leave the page hidden forever. Each repoless site only ever resolves to its own brand, so this never fetches another brand's CSS — head.html stays completely brand-agnostic either way.

Contrast is per brand, not per component

A shared component inherits different colour values per brand, so passing 4.5:1 for one brand proves nothing about another. This is the accessibility failure that multi-brand architecture makes most likely, and it is invisible unless you check each brand separately.

The friction list is the point

Whatever slowed this onboarding down is the framework's remaining debt, and it is the only honest measure of whether the architecture works. Fix the top item before the next brand arrives.

Reference · The Divergence Ladder

Start at the bottom. Stop at the first rung that works. Never skip.

When two brands need something different, climb. The rung you stop at goes in the pull request description. Most requests that arrive sounding like a fork are L0 plus L2.

Cost of divergenceL0 → L4 · ONGOING COST INCREASES
L0free

Different document, fragment, or sheet. Markup shape identical; only words, images, and links differ.

L1free

Colour, type, spacing, radius, elevation, logo — including component tokens, which absorb far more than people expect.

L2~10 lines

An author writes Cards (compact); EDS produces .cards.compact. Layout or density differs, behaviour identical.

L3one branch

L4forever
Fork — requires an ADR

All four must hold: more than ~40% of the JavaScript differs; the difference is structural, not visual; L0–L3 were genuinely attempted and the attempt is described in the pull request; and an ADR exists, is linked in a header comment in the block's JS, and names an owner and a review date.

Worked example: two very different headers

One brand has a flat navigation bar; another has a mega-menu with an embedded search. This is the case that usually triggers a fork request. It is L0 + L2 + L3.

export default async function decorate(block) {
  const { pathPrefix } = getBrandConfig();

  // L0 — the nav document differs per brand; metadata points at it
  const navPath = getMetadata('nav') || `${pathPrefix}/nav`;
  const html = await fetch(`${navPath}.plain.html`).then((r) => (r.ok ? r.text() : ''));
  if (!html) return;

  const nav = document.createElement('nav');
  nav.innerHTML = html;

  // L2 — the block derives its variant from the shape of the content
  const isMega = [...nav.children].some((s) => s.querySelector('ul ul'));
  block.classList.toggle('header--mega', isMega);

  // L3 — capability, not brand name
  if (hasFeature('storeLocator')) nav.append(await buildLocator(pathPrefix));

  decorateIcons(nav);
  block.append(nav);
}

One block, three mechanisms, zero forks. A third brand with a flat nav and no locator is a registry entry and a nav document.

The component tier is what prevents forks

A block writes border-radius: var(--card-radius, var(--radius-m)). A brand needing squared-off, borderless cards overrides three lines in its own token file. No variant, no fork, no shared file touched. Before proposing anything above L1, check whether three component tokens would have done it. They usually would.

.card {

  --card-radius:  var(--radius-m);
  --card-padding: var(--space-4);
  --card-border:  1px solid var(--color-border);

  background: var(--card-bg);
  border-radius: var(--card-radius);
  padding: var(--card-padding);
  border: var(--card-border);
}

:root[data-brand='beta'] {

  --card-border: none;

Scoped brand overrides

For a tweak too specific to deserve a token, put it in the shared block's CSS, scoped to the brand attribute, capped at roughly 20% of the file. Past that cap the block is telling you something: promote the difference to a component token, or accept that it has genuinely diverged. A block whose CSS is half brand overrides is a fork nobody declared.

[data-brand='beta'] .header .nav-tools { order: -1; }

Reference · Standards & budgets

EDS is fast because it does almost nothing

JavaScript

  • ES modules, no build step. No transpiler, bundler, or framework.
  • ESLint Airbnb base, zero warnings. An inline disable needs a comment saying why.
  • No default exports except a block's decorate.
  • No new dependency without an ADR. Every kilobyte is on the critical path for every brand.
  • No secrets — these repositories are usually public. Endpoints come from the registry, credentials from an edge worker.
  • Fail soft. Authors produce shapes you did not anticipate, and a block that throws takes the page with it.

CSS

  • Custom properties for anything themable. Structural values no brand would change stay literal.
  • Component tokens declared at the top of each block's CSS.
  • Logical properties for layout, so right-to-left costs nothing.
  • Every selector scoped to the block. No !important without a comment.

Markup, UI, accessibility

  • The authored DOM carries meaning. Transform it, do not rebuild it.
  • Buttons act, links navigate. A <div> with a click handler is a review finding.
  • One <h1>, heading order unbroken, correct landmarks.
  • Images through createOptimizedPicture with explicit width and height.
  • WCAG 2.2 AA: keyboard operable, visible focus, accessible names, prefers-reduced-motion respected, live regions for async updates.
  • Empty and error states say what happened and what to do next.
  • Motion answers an action. Decorative entrance animations on every section are noise.

Eager loads only what the LCP needs. Lazy loads everything else. Delayed carries every third-party tag without exception — analytics, chat, consent, tag managers. Governance

  • ADRs in docs/adr/, numbered, immutable once accepted, superseded rather than edited. Required for any fork, any contract change, any new dependency, any change to brand resolution.
  • New shared blocks need a short RFC: what it does, why no existing block covers it, which brands need it, its token surface.
  • CODEOWNERS mirrors the layer model — shared blocks need a platform reviewer, brand token files and forked blocks need that brand's team.
  • Deprecation is explicit: marked in the README and model, kept a quarter, then removed. Every fork carries a review date from the day it is created.

Failures that are quiet rather than loud
